(RPH-DOC-000 L1785-L1840) — UX doctrine: context separation mirrors the ontology's authority separation.

## VOCABULARY

- "Janumi: The company and product family." "Janumi Platform: The shared multi-tenant infrastructure, runtime, commercial, integration, and operational foundation." "Janumi Professional Workbench: The general-purpose environment for designing and operating Professional Work Architectures and Undertakings." "Recursive Professional Harness: The control architecture underlying recursive execution, assurance, governance, and recovery." (RPH-DOC-000 L2000-L2014) — Top-of-ladder canonical definitions; company ≠ platform ≠ workbench; RPH is control architecture, not a product.
- "Professional Work Architecture: A reusable, versioned architecture defining how a class of professional work is structured and governed." "Professional Work Unit: A bounded, executable, assessable, and traceable unit of professional work." (RPH-DOC-000 L2016-L2022) — PWA/PWU canonical definitions: class-level versioned architecture; four defining PWU qualities.
- "Undertaking: A concrete body of professional work instantiated under a PWA." "Professional Work Graph: The instantiated semantic graph of professional-work objects within an Undertaking." "Execution Workflow: The temporal process through which PWUs are performed." (RPH-DOC-000 L2024-L2034) — Instance-level triple: Undertaking owns the graph; workflow is temporal machinery only.
- "Domain Product: A specialized Janumi product combining domain PWAs, views, policies, integrations, and execution capabilities." (RPH-DOC-000 L2036-L2038) — Domain product definition; a bundle, never a single PWA or view.
- "A Product Shape Package is a governed export of the shape-engineering outputs of a Product Realization Undertaking. It may stop short of implementation or include implementation-ready planning." "Product Shape Package describes and governs what should be built / Implementation Package contains or enables the built realization" — "related but distinct." (RPH-DOC-000 L1366-L1370, L1443-L1451) — Canonical pre-implementation handoff export; non-equivalent to the Implementation Package.
- "A **Reference Fixture** is a representative Undertaking used to test or demonstrate a PWA... It must always be labeled as an instance or fixture. It must not be presented as the PWA definition itself." (RPH-DOC-000 L1767-L1781) — Fixture vocabulary; Field Service example is an instance, never the definition.
- "Assurance evaluates claims using evidence under policies. It does not merely mark tasks as passed or failed." "Governance is the exercise of authority over: approval; rejection; waiver; escalation; residual risk; baseline promotion; revocation; supersession." (RPH-DOC-000 L1509-L1526) — Canonical assurance/governance split: evidence-based evaluation vs. exercise of authority.
- Migration table: "Lens as work architecture → Professional Work Architecture"; "Product Lens → Product Realization PWA"; "Lens Designer → PWA Designer"; "Security lens as work architecture → Security Maintenance PWA"; "Security lens as UI filter → Security View or Security Viewpoint." (RPH-DOC-000 L1561-L1591) — Retires all 'Lens' terminology; the same legacy word splits into architecture vs. projection senses.
- Migration table: "Validator → Implementation of an Assurance Policy"; "Phase → Derived compatibility milestone where legacy support is required"; "Replan phase → Controller action, not a universal professional-work phase"; "Commit phase → Repository operation plus separate baseline governance." (RPH-DOC-000 L1587-L1590) — Legacy engine vocabulary demoted: validators are policy implementations; phases are not ontology.
- Migration table: "Workflow for full professional structure → PWA or Professional Work Graph"; "Workflow for temporal execution → Execution Workflow"; "Workflow Canvas as ontology → Execution View or projection only." (RPH-DOC-000 L1575-L1577) — Disambiguates the overloaded 'workflow' into three canonical treatments.
- Naming rules: domain products use branded names (JanumiCode, JanumiLegal...); work architectures use "functional names ending in `PWA`"; Undertakings use "the concrete objective plus `Undertaking`"; views end in "`View`, `Explorer`, `Studio`, or `Workbench`"; packages end in "`Package`." (RPH-DOC-000 L1594-L1647) — The complete canonical naming grammar by object kind.
- "The output product should be named separately from the Undertaking." An Undertaking may produce "software; service; policy; legal instrument; construction outcome; analysis; operational capability; professional recommendation; shape package. The output type depends on the PWA." (RPH-DOC-000 L1477-L1503) — Undertaking ≠ its product; output vocabulary is profession-generic.
- "JPWB general professional-work environment / JanumiCode software-product specialization of JPWB" with JPWB providing generic authoring/operation/assurance/governance/baselines/traceability and JanumiCode adding software-product PWAs, coding-agent roles, repository integrations, IDE surfaces, V&V, etc. (RPH-DOC-000 L1687-L1721) — Canonical generic-vs-specialization split of responsibilities.
- "A template is not necessarily a complete PWA." A profile is "a bounded configuration of a PWA" that may alter "required PWUs; assurance rigor; evidence requirements; human authority; execution strategies; baseline requirements." (RPH-DOC-000 L1173-L1207) — Template vs. profile vs. PWA distinctions in the customization vocabulary.

## SEMANTIC-INVARIANTS

- "Product Realization PWA is not synonymous with JanumiCode." and "JanumiCode may contain multiple PWAs." (RPH-DOC-000 L1856-L1858) — Invariants 5-6; kills the most common conflation in legacy docs.
- "A PWU Type belongs to a PWA. A PWU Instance belongs to an Undertaking." plus "An Execution Workflow is temporal machinery, not the PWA itself. A View is a projection, not the underlying PWA or Work Graph." (RPH-DOC-000 L1866-L1872) — Invariants 10-13; type/instance ownership split and the two central non-equivalences (structure ≠ execution ≠ projection).
- "The Field Service Management SaaS Undertaking is not the Product Realization PWA. The Field Service Management SaaS product is not the Undertaking." (RPH-DOC-000 L1874-L1876) — Invariants 14-15; the reference example's own three-way non-equivalence.
- Inherited vs. local: an Undertaking may inherit "PWU Type definitions; decomposition rules; assurance assignments; baseline requirements; role expectations; completion semantics" but owns "PWU Instances; actual boundaries; actual assumptions; actual evidence; actual assessments; actual decisions; actual baselines; actual execution state." (RPH-DOC-000 L1256-L1278) — Definitions inherit downward; all 'actuals' are Undertaking-owned.
- "A specialized view does not by itself constitute a domain product." (RPH-DOC-000 L1737-L1739) — View/product non-equivalence; a projection cannot be promoted to product status.
- "Deployment on Janumi Platform is a supported outcome. It is not an implicit requirement of every Product Realization PWA." Delivery dispositions include "Retain as approved design without implementation." (RPH-DOC-000 L1455-L1473, L1886) — Platform deployment is optional; an Undertaking may legitimately conclude without building anything.

- Conformance checklist: a document, design, UI, or implementation conforms when it satisfies 15 enumerated distinctions (Janumi≠Platform, JPWB≠JanumiCode, PWA vs Undertaking, Types vs Instances, Graphs vs Workflows, views-as-projections, commits≠baselines, no silent PWA propagation, Lens superseded, bootstrap preserved...). (RPH-DOC-000 L2089-L2107) — Operational test for charter conformance; usable as a review rubric.

Use `workflow` "only where temporal execution or approval behavior is intended."

## CONSTITUTIONAL CANDIDATES

- "It becomes Evidence only after evidence admission evaluates provenance, relevance, scope, and limitations." (Executable Invariant and Conformance Test Specification.md L1291-1293) — Artifact/Evidence distinction: evidence is an admitted status, not a produced thing.
- "It must prove that the system refuses to confuse: an instruction with intent; a task with professional obligation; an output with evidence; evidence with proof; validator prose with assurance; execution success with satisfaction; human preference with authority; a commit with an accepted baseline; an Execution Workflow visualization with the professional work itself." (Executable Invariant and Conformance Test Specification.md L2561-2573) — The nine executable distinctions; the whole suite's purpose statement.
- "a validator recommends `SATISFIED`. And one blocking criterion is `NOT_MET`. Then the Assurance Service rejects the recommendation and produces `REJECTED`." (Executable Invariant and Conformance Test Specification.md L1350-1362) — Validator recommendation is never authoritative disposition; policy criteria outrank validator prose.
- "a Product Owner agent recommends approval. Then no effective governance decision exists until an authorized actor approves it." (Executable Invariant and Conformance Test Specification.md L1507-1515) — Recommendation is not approval; authority is positional, not persuasive.
- "source code or architecture artifacts are committed to version control. Then no baseline becomes authoritative without promotion decision and assurance." (Executable Invariant and Conformance Test Specification.md L1692-1700) — Commit ≠ baseline; authoritative status requires decision plus assurance.
- "executionState = SUCCEEDED must never alone cause: assuranceState = SATISFIED" (Executable Invariant and Conformance Test Specification.md L2279-2291) — Property P1: execution never implies assurance, stated as a universal property over all legal command sequences.
- "five required policies: four satisfied; one rejected. Then aggregate assurance is rejected." (Executable Invariant and Conformance Test Specification.md L1470-1481) — Policy composition takes the strictest unresolved disposition; no majority or averaging; likewise "a critical open observation ... aggregate assurance cannot be `SATISFIED`" (L1407-1415).
- "both remain visible; aggregate state becomes contested, inconclusive, or escalated; results are not averaged silently." (Executable Invariant and Conformance Test Specification.md L1452-1466) — Conflicting valid assessments are preserved and escalated, never reconciled by suppression.
- "a mandatory criterion result `UNABLE_TO_DETERMINE`. Then the assessment cannot become satisfied." (Executable Invariant and Conformance Test Specification.md L1366-1374) — Uncertainty fails closed; unable-to-determine is never treated as met.
- "the finding remains visible; disposition becomes `WAIVED`; rationale and authority are recorded; evidence is unchanged." (Executable Invariant and Conformance Test Specification.md L1535-1546) — Human override waives disposition but never erases findings or evidence.
- "A decision approving semantic version `n` never authorizes semantic version `n+1`." (Executable Invariant and Conformance Test Specification.md L2326-2328) — Property P5: approvals bind exact semantic versions; no approval carry-forward.
- "No legal command mutates an authoritative baseline's item set." (Executable Invariant and Conformance Test Specification.md L2340-2342) — Property P7: authoritative baselines are immutable; change requires a successor.

## DOCTRINE-CONOP

- "Mutations that must be caught include: removing the assurance check before PWU satisfaction; ... treating `UNABLE_TO_DETERMINE` as `MET`; allowing expired waivers; ... dropping mandatory constraints during decomposition." (Executable Invariant and Conformance Test Specification.md L2355-2366) — Mutation testing targets the guards whose silent removal would hollow the harness.
- "Critical domain modules should achieve a high mutation score, not merely line coverage." (Executable Invariant and Conformance Test Specification.md L2368) — Test-quality doctrine: coverage numbers alone are insufficient proof.
- "State-transition guards 100% ... Assurance disposition engine 100% ... Line coverage alone is not sufficient." (Executable Invariant and Conformance Test Specification.md L2378-2389) — Branch coverage is mandated at 100% precisely on decision logic; UI is risk-based.
- "Builders should default to valid minimum objects. Tests that need invalid objects should modify one characteristic deliberately. This keeps failures attributable." (Executable Invariant and Conformance Test Specification.md L2415-2419) — Test-data doctrine: single-deliberate-defect construction for attributable failures.
- "Do not mock away domain boundaries in integration tests." (Executable Invariant and Conformance Test Specification.md L2438) — Test doubles simulate external actors (models, validators, humans, tools), never internal domain seams.
- "A failed conformance test should identify: test ID; architectural rule; ... semantic versions; relevant trace links; invariant violated." (Executable Invariant and Conformance Test Specification.md L2497-2507) — Failure reports name the violated architectural rule, not just the assertion.
- "CI fails when an architectural invariant is violated." (Executable Invariant and Conformance Test Specification.md L2555) — Definition-of-Done item 17: invariants are pipeline-enforced, not review-enforced; DoD 14 also requires demonstrating execution-success-with-assurance-failure end-to-end (L2552).

## SEMANTIC-INVARIANTS

- "a policy requiring `DIFFERENT_AGENT`. And the same producing agent is selected as validator. Then evaluation is blocked; `INDEPENDENCE_VIOLATION` is recorded; a different validator or waiver is required." (Executable Invariant and Conformance Test Specification.md L1332-1346) — Producer cannot validate own work when independence is required; only substitution or waiver clears it.
- "a validator times out. Then assessment state becomes `VALIDATOR_FAILED` or returns to ready for retry. The assessed work is not automatically rejected." (Executable Invariant and Conformance Test Specification.md L1378-1388) — Validator infrastructure failure is not a judgment about the work.
- "a validator returns malformed JSON. Then output is rejected; no authoritative observations are created; no assurance disposition changes; diagnostic evidence is retained." (Executable Invariant and Conformance Test Specification.md L1392-1403) — Malformed validator output can never mutate authoritative state, yet is retained diagnostically.
- "an assessment is conditionally satisfied ... the condition remains visible in: assessment; PWU assurance view; review package; baseline package." (Executable Invariant and Conformance Test Specification.md L1419-1432) — Conditional assurance stays conditional and visible at every consuming surface.
- "an assessment of Architecture semantic version 2. When Architecture version 3 is created. Then the version-2 assessment cannot satisfy version 3." (Executable Invariant and Conformance Test Specification.md L1436-1448) — Semantic change invalidates prior assessments; assurance binds versions like approvals do.
- "a waiver for policy criterion `AC-04` on Architecture version 2. Then it does not waive: another criterion; another object; Architecture version 3." (Executable Invariant and Conformance Test Specification.md L1550-1562) — Waivers are scoped to criterion, object, and version — never blanket; and they expire: "a required waiver is expired ... promotion is rejected" (L1566-1578).
- "the decision is revoked. Then Architecture Baseline becomes review-required or revoked; downstream planning is impacted; impact analysis is initiated." (Executable Invariant and Conformance Test Specification.md L1582-1596) — Revoking a decision propagates: dependent baselines and planning cannot silently keep standing on it.
- "the original baseline is unchanged. A successor baseline must be created." (Executable Invariant and Conformance Test Specification.md L1674-1688) — Baseline change is supersession, never mutation; "Baseline 1 remains queryable; supersession trace exists" (L1704-1714).
- "Originating expression → approved intent → Architecture PWU → Architecture Artifact → Claim → Evidence → Assurance Assessment → Approval Decision → Architecture Baseline" (Executable Invariant and Conformance Test Specification.md L1722-1734) — The canonical typed traceability chain every authoritative baseline must exhibit; artifacts with no producing PWU fail validation (L1744-1748).
- "When its relation is corrected. Then a replacement or superseding link is created; the old link is not overwritten silently." (Executable Invariant and Conformance Test Specification.md L1752-1758) — Trace links are immutable; correction is supersession. Invalidated evidence propagates downstream: "claim support is no longer valid" (L1762-1766); Property P4 forbids satisfied assessments relying exclusively on invalidated evidence (L2318-2322).
- "commands continue to validate against canonical aggregate state, not stale projection state." (Executable Invariant and Conformance Test Specification.md L1881-1889) — Projections are read-only derivations; lag can never alter authoritative decisions.
- "the external operation's completion is uncertain. ... the attempt enters a reconciliation state. The system must not blindly repeat the side effect." (Executable Invariant and Conformance Test Specification.md L1927-1946) — Restart during model invocation forces reconciliation, never blind re-execution; pending human decisions likewise survive restart without duplicate requests (L1949-1962).
- "The UI cannot show an unqualified green completion indicator when execution succeeded but assurance remains incomplete." (Executable Invariant and Conformance Test Specification.md L1995-1997) — Projection-level enforcement of exec≠assurance: the UI must display execution, assurance, and shape-integrity states distinctly (L1983-1991).
- "Moving a node: updates presentation revision; does not change semantic version; emits no PWU semantic event; does not invalidate assurance." (Executable Invariant and Conformance Test Specification.md L2011-2018) — Presentation independence: layout is a separate revision plane from semantics (also Property P8, L2346-2348).
- "Changing the legacy compatibility phase field directly must not mutate PWU or assurance state." (Executable Invariant and Conformance Test Specification.md L2038-2040) — Compatibility milestones (INTAKE, ARCHITECTURE, REPLAN) are derived projections, never stored lifecycle state (L2030-2060).
- "every mandatory parent obligation has exactly one or more valid dispositions: allocated; retained; satisfied; authorized waiver." (Executable Invariant and Conformance Test Specification.md L2295-2302) — Property P2: obligations never vanish in decomposition; P3 gives constraints the parallel closed disposition set including "inapplicable with valid rationale" (L2306-2314).
- "Executing the same idempotency key multiple times produces the same business result and no additional domain events." (Executable Invariant and Conformance Test Specification.md L2332-2336) — Property P6; retries can never create two effective decisions or two authoritative baselines (L1813-1821).
- "The deferred offline capability must remain represented as: assumption or constraint; residual condition; baseline scope statement; future implementation obligation" (Executable Invariant and Conformance Test Specification.md L2109-2116) — Deferred scope must stay explicit in every artifact layer; deferral is never silent deletion.
- "assumption becomes falsified; intent is revised; impact analysis identifies architecture and behavior PWUs; Architecture Baseline remains immutable but review-required; ... stale approval is not reused." (Executable Invariant and Conformance Test Specification.md L2191-2198) — Falsified material assumptions cascade through intent, impact analysis, and successor work without mutating history.

## PROTOCOL-PRACTICE

- "domain events and outbox rows are committed atomically. A transaction rollback leaves neither persisted." (Executable Invariant and Conformance Test Specification.md L1867-1877) — Outbox atomicity; replay reconstructs state equal to materialized state (L1836-1848); event revisions contiguous (L1825-1829).
- "the registered upcaster produces the current internal representation without rewriting the event." (Executable Invariant and Conformance Test Specification.md L1893-1905) — Event history is never rewritten; schema evolution happens at read time.

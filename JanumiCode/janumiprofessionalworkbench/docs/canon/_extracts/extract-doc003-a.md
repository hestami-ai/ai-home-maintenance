## CONSTITUTIONAL CANDIDATES

- "The Product Realization PWA is therefore not: a fixed workflow; a sequence of prompts; a collection of agent roles; a canvas template; a task list; a project-management methodology. (RPH-DOC-003.md L34-43) — Negative definition guarding the PWA's ontological altitude against workflow/prompt/agent-role capture.

- "Relationships must remain typed and traceable. Generic untyped links are insufficient for authoritative reasoning." (RPH-DOC-003.md L353) — Constitutional graph rule: authority requires typed, traceable edges.

- "A decision must not be represented merely as text embedded in an architecture document when it materially affects downstream work." (RPH-DOC-003.md L830) — Material architecture decisions are first-class Professional Work Objects, never prose-only.

## DOCTRINE-CONOP

- "The Recursive Professional Harness defines how professional work is represented, executed, assured, revised, and promoted into authoritative state. The Product Realization PWA defines: what product-development work exists; which professional concepts are meaningful ... how child outcomes recompose into a completed product outcome." (RPH-DOC-003.md L18-32) — The PWA/RPH division of labor: RPH = how, PWA = what.
- "Product Realization PWA ↓ PWU Types Artifact types Claims Evidence expectations Assurance policies Decomposition rules Role defaults ↓ Recursive Professional Harness ↓ Execution plans Runtime bindings Assurance assessments Governance decisions Baselines" (RPH-DOC-003.md L94-112) — The supply chain: PWA feeds seven semantic categories into RPH, which produces runtime outcomes.
- "The Product Realization PWA supports three conformance profiles." [Lightweight / Standard / High-Assurance] (RPH-DOC-003.md L129-193) — Proportional-assurance doctrine: expectations scale from explicit-intent+local-evidence to independent assurance, rollback, and residual-risk decision.
- "The required profile is selected using consequence, uncertainty, irreversibility, security sensitivity, and regulatory exposure." (RPH-DOC-003.md L195) — The five profile-selection criteria; risk drives conformance level, not preference.
- "Product Realization PWU Type ├── Intent and Product Definition ... ├── Product Behavior Definition ... ├── Architecture Definition ... ├── Implementation Planning ... ├── Product Implementation ... ├── Integrated Product Validation ... └── Product Baseline Promotion PWU Type" (RPH-DOC-003.md L371-380) — The canonical seven-branch standard semantic decomposition of the Product Realization root.
- "This hierarchy describes reusable semantic composition in the PWA. When the PWA is instantiated as an Undertaking, each required node becomes a concrete PWU Instance in that Undertaking's Professional Work Graph." (RPH-DOC-003.md L382) — Type-vs-instance doctrine: PWA composition is a template; Undertakings instantiate it into the work graph.
- "It does not require that every child execute strictly in sequence. For example: architecture analysis may expose missing product requirements; implementation planning may trigger architecture revision; validation may create new implementation PWU Instances" (RPH-DOC-003.md L384-392) — Non-linear execution doctrine: the tree is semantic composition, not a pipeline; feedback loops are expected.
- "A successful Product Realization Undertaking must establish more than the existence of working code. It must establish justified confidence that: the intended problem was understood; the desired outcomes were preserved ... acceptance was granted by appropriate authority; the promoted baseline is traceable to the originating intent." (RPH-DOC-003.md L72-86) — Mission doctrine: success = justified confidence across eleven conditions, not shipped code.
- "Children are generated from the approved implementation decomposition" ... "Implementation agents may propose: reshaping; new child PWU Instances; additional constraints; architecture revision; clarification; alternative plans." (RPH-DOC-003.md L963, L1000-1007) — Implementation children derive from an approved plan; agents get an enumerated feedback channel, pairing with the L1009 silent-change prohibition.

## VOCABULARY

- "Product Intent: The authorized description of the problem, desired outcomes, users, constraints, non-goals, and success conditions." (RPH-DOC-003.md L203-205) — Root concept everything traces to; "authorized" makes it a governed object, not a paraphrase.
- "Baseline: An approved and immutable version of one or more product artifacts that serves as an authoritative reference." (RPH-DOC-003.md L281-283) — Approval + immutability jointly define authoritative state; neither alone suffices.
- "Architecture Decision: A governed choice among materially different architectural alternatives." (RPH-DOC-003.md L253) — "Materially different alternatives" is the load-bearing test for what counts as a decision.

## SEMANTIC-INVARIANTS

- "A root PWU Instance of this type may be satisfied only when: each mandatory child obligation is satisfied, waived, or superseded; integrated validation supports the root completion claim; no unresolved blocking assurance observations remain; an authorized baseline-promotion decision exists." (RPH-DOC-003.md L447-452) — The root recomposition rule: four jointly necessary conditions; satisfied/waived/superseded is the exhaustive disposition set.
- "The promoted product baseline satisfies the approved Product Intent within its authorized boundaries and residual uncertainty." (RPH-DOC-003.md L423) — The root completion claim all evidence must ultimately support; bounded by authority and disclosed uncertainty.
- "Intent DEFINES Desired Outcome ... User Journey REALIZES Capability. Capability REFINED_BY Requirement. Requirement ALLOCATED_TO PWU Instance. PWU Instance PRODUCES Artifact ... Artifact SUPPORTS Claim. Assurance Assessment VERIFIES Claim. Decision APPROVES Baseline." (RPH-DOC-003.md L291-331) — The traceability spine: intent→journey→capability→requirement→work→artifact→claim→assurance→decision→baseline.
- "Create bounded child PWU Instances that collectively satisfy a parent PWU Instance's obligation." [Required outputs include] "constraint propagation; assumption propagation ... recomposition contract; coverage claims; retained parent obligations." (RPH-DOC-003.md L896-909) — Decomposition invariant: obligations, constraints, and assumptions propagate down; a recomposition contract and retained parent obligations must exist.
- "Coverage ... Cohesion ... Coupling ... Granularity ... Boundary clarity ... Recomposition feasibility: Can assured child outputs be integrated into a parent result? Traceability: Can each child explain why it exists?" (RPH-DOC-003.md L911-939) — Seven decomposition quality attributes; recomposition feasibility and per-child existence justification are the distinctive invariants.
- "A PWU Instance of this type must distinguish: user-stated facts; inferred needs; proposed interpretation; unresolved ambiguity; optional enhancement; imposed technical solution." (RPH-DOC-003.md L535-542) — Intent Discovery epistemic taxonomy: six statement classes that must never be conflated.
- "decomposition preserves parent obligations ... execution plans do not silently change product semantics." (RPH-DOC-003.md L871-877) — Planning claims: plans are semantics-preserving transformations, never semantic edits.
- "Promotion conditions: no unresolved critical finding; blocking findings resolved or authorized through waiver; required assessments complete; baseline items identified and immutable; decision authority valid; promoted version matches reviewed version; rollback or recovery exists where required; residual uncertainty accepted." (RPH-DOC-003.md L1116-1125) — Eight promotion gates; promoted-version=reviewed-version blocks review-then-swap.
- "Artifacts must have: identity; provenance; content hash where applicable; semantic version; producing PWU Instance; applicable claims; status; supersession history." (RPH-DOC-003.md L1214-1223) — Universal artifact obligations; provenance ties every artifact to the work that produced it.
- "Not every journey requires every class, but inapplicability must be explicit." (RPH-DOC-003.md L646) — No silent omission: scenario classes are opted out explicitly, never skipped implicitly.

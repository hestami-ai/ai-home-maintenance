# JPWB-REG-005 — Decision and Divergence Register

## 0. Closure rule

**Entries close by being merged into governing artifacts. A ruling may never float outside the canon.** A decision that lives only in a conversation, a commit message, a guide, or this register is not yet law: it must be merged into the artifact that owns its concern (JPWB-CON-000 / DOC-001 / DOC-002 / DOC-003 / DOC-004, or the repository for shapes), and the entry here records the merge. This rule exists because rulings that floated outside the canon have already been lost once (the chain-of-thought ruling, REG-Q-027). The register is the ledger, never the statute book.

Non-example: this rule does not require re-ratifying a ruling each time it is restated. Once merged, the governing artifact's text is the authority; the entry here is closed history.

Non-example: the closure rule governs adjudications — DECISIONs, OPEN QUESTIONs, and DIVERGENCE FINDINGs whose substance belongs in a governing artifact. Ratification records have no owning artifact to merge into: they ARE the conferral act, are complete upon recording, and live permanently in the register without ever merging.

## 1. Entry discipline

Modeled on the M0 Reconciliation Ratify Sheet: every entry cites its authority, records who acted under what mandate and when, and separates sponsor-pending items explicitly.

Each entry carries: **id · date · type · statement · safe default** (open items only) **· disposition · merge target · status**.

- **Id series:** `REG-D-nnn` decisions, `REG-Q-nnn` open questions, `REG-F-nnn` divergence findings, `REG-E-nnn` elicitation items.
- **Type:** `DECISION` | `OPEN QUESTION` | `DIVERGENCE FINDING` | `PROPOSED REFINEMENT` (per DOC-004 §9.2).
- **Status** (the single normalized enumeration): `OPEN` (live; any recorded safe default binds) · `DECIDED — MERGE PENDING` (ruled; not yet carried by an EFFECTIVE governing artifact — carriage in an unratified draft does not close an entry) · `MERGED` (closed; an EFFECTIVE, ratified governing artifact carries it) · `CLOSED` (resolved without a merge target of its own — e.g., answered by an existing artifact section or mooted by a recorded act, cited in the closure) · `SUPERSEDED` (replaced by a later entry, cited) · `EFFECTIVE` (a conferral, effective on recording; conferrals never merge — §0) · `EFFECTIVE — MERGE PENDING` (effective on recording; incorporation into its named targets pending) · `EFFECTIVE — MERGED` (effective and already incorporated in its targets). *(Vocabulary history, recorded here because §1 predates the entry series and carries no version field: EFFECTIVE variants added by REG-D-014; CLOSED defined and the previously split dual enumeration normalized into this single list by the Cycle-000 micro-hygiene pass — both 2026-07-24.)*
- A **safe default** permits conservative progress without creating new meaning. It is not a resolution. If requested work requires choosing the unresolved shape itself, the agent files or updates the entry, blocks only the dependent work, and delivers everything the safe default permits (JPWB-DOC-004 §3.4).

Context note: the M0 Reconciliation Ratify Sheet stands as the ENTRY-DISCIPLINE precedent — the model this register imitates; its ratification standing (build-agent self-ratification) and its eleven best-judgment items are themselves open per REG-Q-026. The JPWB Implementation Roadmap and Tracker is a status snapshot, not canon.

### REG-D-009 — The three-tier documentation architecture
- **Date:** 2026-07-16 · **Type:** DECISION (sponsor-directed: "Proceed" on the drafted amendment)
- **Statement:** The canon is the **overview tier**, not the whole documentation system. Routed through `validateAgainst`, so the refusal carries `details.issues` in the same shape the payload path produces — which is what the enforcement register's SCHEMA-layer markers (`<issueCode>@<path>`) match against.
  - Each of this entry's measured omissions is now a standing assertion rather than a recorded observation (`command-envelope-validation.test.ts`): the four omissible fields, the undeclared envelope property, the ordering against idempotency, and a control that the well-formed command still creates its aggregate. ### REG-F-012 — An idempotency key reused for a DIFFERENT command silently swallows it, and every column needed to refuse it is already stored
- **Date:** 2026-08-02 (found while dispositioning RPH-PER-002; observed by dispatch, not read) · **Type:** DIVERGENCE FINDING · **Class:** CODE_DIVERGES — canon states the refusal; the engine performs the opposite and reports success.
- **Statement:** **JPWB-DOC-003 §9 PER-5** has three clauses. The engine performs the first two and violates the third:
  1. *"Replaying a mutation with the same idempotency key returns the prior result and produces no additional domain event"* — **PERFORMED.** `command-bus.ts` step 1 returns status `DUPLICATE` carrying the prior receipt's `producedEventIds`; the event count is unchanged and the aggregate does not advance.
  2. *"Retries must never duplicate commits, … baseline promotions, approval decisions, or evidence records"* — performed by the same mechanism.
  3. **_"Reuse of a key with a different payload fails."_ — NOT PERFORMED, and its absence is not inert.** Measured: a `CaptureIntent` for aggregate `int_…FAV` was ACCEPTED under key `SHARED-KEY`; a **second, entirely different** `CaptureIntent` — different payload, different `intentId`, different `targetAggregateId` (`int_…FB0`) — reusing that key returned **`DUPLICATE`**, and `loadObject('int_…FB0')` is **`undefined`**. A real command creating a real object was **discarded**, and the caller was handed the *other* intent's event id as its result.
- **THE DETECTION MATERIAL IS ALREADY PERSISTED AND ALREADY RETURNED.** `command_receipts` stores `command_type`, `target_aggregate_id` and `result_hash`; `getReceipt` reads all three and `CommandReceiptRecord` carries all three; `command-bus.ts` step 1 discards all three and compares nothing but the key's existence. In the measurement above the stored `target_aggregate_id` (`int_…FAV`) and the second command's (`int_…FB0`) differ outright — the refusal PER-5 requires was one comparison away from free. This is the REG-F-010 shape (ratified material present, unread) with a live correctness consequence rather than a diagnostic one.
- **THE FAILURE IS SILENT AT EVERY LAYER ABOVE IT, which is what makes it worth its own entry rather than a note.** `DUPLICATE` is classified as SUCCESS by `Engine.dispatchBatch` (`r.status !== 'ACCEPTED' && r.status !== 'DUPLICATE'` is its only failure test), so a batch containing a key-colliding command **commits and reports `ok: true`**. Nothing logs a warning; `command.duplicate` is an `info`. A caller that generates idempotency keys from anything less than perfectly unique material — a retry wrapper keyed on a request id, a form action keyed on a form id, a seeding script keyed on an ordinal — loses commands and is told it succeeded. This is precisely CON-000 AX-8's "fail closed; escalate rather than invent" inverted: the engine invents an outcome for a command it never ran.
- **This does NOT change RPH-PER-002's disposition, and the distinction is deliberate.** That rule's own ratified statement is the OUTCOME half — *"emits no new domain events and returns the original result"* — which the engine satisfies; the register therefore disposes it `NOT_A_COMMAND_REFUSAL` and records the enforcement site. The refusal clause is **canon's addition**, so folding it into that row would let a rule whose own statement holds carry a disclosure about a different sentence — the subject substitution this register records four times over.
- **A LAYER CORRECTION FALLS OUT OF THE SAME MEASUREMENT.** The register's RPH-EXE-007 row said the adjacent idempotency guarantee "is covered at the store layer". The DECISION is at the **COMMAND** layer — `command-bus.ts` step 1, in `packages/rph-application/` — and only the receipt LOOKUP is the store's. Corrected in the same commit; a register whose entire purpose is layer precision may not be loose about its own.
- **Disposition:** ~~Recorded, not fixed.~~ ~~**FIXED 2026-08-04 for two of PER-5's three dimensions.**~~ **FIXED 2026-08-04 for ALL THREE.** The prescription below was followed as written and is kept unstruck because it was right.
  - **THE SURVEY.** Instrumented across the whole suite: exactly **TWO** dispatches ever reach the duplicate path, and **both are true replays** (same command type, same target). No caller anywhere reuses a key across commands, so this refuses nothing the engine accepted — and the full suite confirmed it, passing unchanged.
  - ~~**TWO OF THREE DIMENSIONS, and the third is named rather than approximated.**~~ `commandType` and `targetAggregateId` are compared before returning `DUPLICATE`. ~~The third — *same command, same target, different **payload*** — still replays.~~ **THE THIRD IS NOW CLOSED TOO**, and the cost stated below was the cost paid: the receipt's `resultHash` is `contentHash(nextState)` — the RESULTING OBJECT — so it could never decide the payload question, because having it means having executed the command. What closed it is `command_receipts.payload_hash`, holding `contentHash(command.payload)`.
  - **AND THAT REQUIRED THE FIRST FORWARD MIGRATION THIS ENGINE HAS EVER RUN, which is most of the work.** `SCHEMA_VERSION` had been `1` since W2-INC-1, so "bump this and register a forward migration" was an instruction nothing had followed: the adapter's older-than arm **threw**, and its `user_version = 0` arm **stamped without migrating**. Both were correct while the baseline was the only version, and both become wrong at v2 — a durable store (`apps/rph-demo` opens one by filename) would either refuse to open or come up stamped v2 with a v1 table. So: a `MIGRATIONS` ladder, a **pure** `planMigration` that refuses a gap rather than skipping it, and a distinction the constructor has to capture **before** `SCHEMA_SQL` runs — because every statement there is `CREATE … IF NOT EXISTS`, which erases the difference between a brand-new file and a store that predates versioning. Both report `user_version = 0`; only one of them needs the ALTER.
  - **ABSENCE IS SKIPPED, NOT FAILED, and it is the one design decision here that could have gone wrong quietly.** Receipts written before v2 carry NULL. Reading that as *"the payload differed"* would refuse every legitimate replay in an upgraded durable store — a regression against RPH-PER-002's **ratified** contract, manufactured out of an absence. This register has recorded that mistake more than once, so the guard is `prior.payloadHash !== undefined && …` and it has its own mutant: drop the first clause and exactly one test reddens.
  - **THE HONEST COST, WHICH IS A REAL TIGHTENING RATHER THAN PLUMBING.** `contentHash` canonicalizes, and canonical JSON admits only **finite integers** — so hashing an arbitrary payload can throw, and doing that unguarded in `dispatch` would reopen REG-F-011's crash class *while fixing a different finding*. The bus therefore **refuses** a payload it cannot canonicalize (`RPH_VALIDATION_SCHEMA_FAILED`), which converts what was already a crash for state-carrying handlers into a classified refusal. Measured before shipping: **0 of 16,612** dispatches across the suite fail to canonicalize. It also keeps NULL meaning exactly one thing — receipting an unhashable payload with a NULL hash would be a **bypass**: claim a key with a float, and every later reuse of that key skips the payload comparison. **This exposed REG-F-018**, below.
  - **THE CODE QUESTION, ANSWERED THE CONSERVATIVE WAY.** `RPH_IDEMPOTENCY_CONFLICT` is not among the ratified fifteen and minting one is a sponsor act; `RPH_IDEMPOTENCY_DUPLICATE` is ratified but belongs to the REPLAY, which REG-F-010 group 1 records as correctly carrying no error at all. So the refusal uses `RPH_VALIDATION_SEMANTIC_FAILED` and carries `IDEMPOTENCY_KEY_REUSED` in the message — the WP-11 discipline this entry named.
  - **Red-first**, with both controls already passing before the fix — the shape that shows the controls discriminate. Two mutants: neutralising the `commandType` comparison reddens only the different-command test; neutralising `targetAggregateId` reddens only the different-target test. The replay control (prior result, no new event, no error — RPH-PER-002's ratified contract) stays green throughout.
  - **NINE MUTANTS FOR THE PAYLOAD DIMENSION AND THE MIGRATION**, four of which redden **exactly one** test each — the one they target: neutralise the payload comparison → only *different payload* reddens; drop the absence guard → only *pre-v2 receipt replays* reddens; let the canonicalization failure throw → only *refused, not thrown* reddens; make `hasExistingSchema` always false → only *pre-versioning store is migrated* reddens. **The one that is worth reading twice is the constant-payload-hash mutant: it did NOT redden the payload test.** Storing `contentHash({})` for every receipt makes the comparison fire on every replay, so the test asserting a refusal still passes — and the three *replay* CONTROLs go red instead. A payload check with no control would have certified a broken implementation.
  - **AND THE MUTANT HARNESS ITSELF WAS WRONG FIRST.** Its initial run reported *"no test reddened"* for all nine — which, taken at face value, would have read as nine dead assertions and sent me rewriting sound tests. It printed no test counts either, and that is what gave it away: the subprocess was passing `--reporter=basic`, which vitest 4 does not have, so every run died at startup. Recorded because the failure mode is generic and quiet — **a harness that reports nothing looks exactly like a harness that found nothing**, and only the missing *counts* distinguished them.
- **AN OBSERVATION ABOUT THE INSTRUMENT, not this defect.** Canon PER-5 states the reuse rule, and **no rule in the ratified M12 catalog instantiates it**: `RPH-PER-002` states only the replay contract (same command → prior result), and nothing states "a key reused for a different command fails". So the enforcement register **cannot** carry this refusal as a row — there is no rule id to hang it on. That is the inverse of the usual gap this programme finds: not a ratified rule nothing enforces, but an enforced canon obligation no ratified rule names.
- **A FINDING THAT DISSOLVED UNDER ITS OWN TEST, recorded because the near-miss is the useful part.** While closing the payload dimension, a survey reported that **257 of 16,453** receipts store a `target_aggregate_id` differing from the command's declared `targetAggregateId` — `kit.ts` writes `args.aggregateId` (what the handler WROTE) into a column the bus compares against what the command DECLARED. That read as a **false-refusal defect in this entry's own remediation**: a true replay of `DefinePwuType` / `EditPwuType` / `RemovePwuType` refused as `IDEMPOTENCY_KEY_REUSED`, invisible to the suite (nothing replays those) and reachable from the demo's `ui-idem-*` keys. A second column, `command_target_aggregate_id`, was designed and about to be written.
  - **It is not a defect.** The test written to be its red came back **GREEN**, so the *dissolution* got the verification the claim had not: (a) the receipt was read directly — for `DefinePwuType` it holds the PWU_TYPE, i.e. the declared target; (b) the mechanism was traced — `bumpPwaSemanticVersion` derives a **separate** command with `idempotencyKey: ${key}#pwa-version` and commits the PWA under *that* key, which is why two commits in one dispatch do not collide on a primary-keyed receipt table; (c) the survey was **re-run recording `commandId`**, and **all 259** mismatches are `#pwa-version` commands. **Zero primary receipts mismatch.**
  - So the existing column already holds what the bus compares, and the second column would have been **schema added for a defect that does not exist**. The test is kept — retargeted at the property that *is* real and load-bearing (the suffix is what keeps the derived commit out of the outer command's receipt), and it has its own mutant: remove the suffix and the derived insert collides on `command_receipts.idempotency_key`.
- **Merge target:** Repository — `command-bus.ts` (the comparison + the hashability gate), `packages/rph-persistence/src/schema.ts` + `sqlite-storage-adapter.ts` (v2, `MIGRATIONS`, `planMigration`, the pre-existing-schema detection), `packages/rph-ports/src/ports/storage.ts` (`payloadHash`), `kit.ts` (the write), and the tests `idempotency-key-reuse.test.ts` + `schema-migration.test.ts`. JPWB-DOC-003 §9 PER-5 is unchanged and correct. **Status:** **CLOSED** — all three dimensions of PER-5 are performed.

- **THE COMMENT ON THAT LINE ALREADY NAMED THE HAZARD, IN THESE WORDS: *"a resolver that cannot dissent is a resolver that launders whichever side it was pointed at."*** It was written after the overwrite erased a real contradiction (`MarkPwuReady → PwuStateChanged` in the command entry vs `→ PwuMarkedReady` in the table; the command entry was the wrong side, and an *earlier* comment had invented a "display alias" theory to explain the drift away). **The hazard was diagnosed, written down, and the behaviour left in place — so it laundered again.** A documented hazard is not a mitigated one, and this is the second finding in two days where the record already contained the answer.
- **AND THE TEST THAT WATCHED IT WAS UNFALSIFIABLE.** `messages.test.ts` asserted `expect(binding.eventType).toBe(cmd[ct].emitsEvent)` — **the exact identity the generator forced.** It could not fail for any vocab, and it stayed green throughout. It also used `.find()`, reading only the FIRST row per command, so the wrong row was doubly invisible. This is the `a-control-that-cannot-fail` shape at the contract layer.
- **THE VOCAB WAS RIGHT THE WHOLE TIME, AND SAID SO.** The dropped row carries its own note: *"So ONE command produces TWO events … Recorded HERE, unemitted, so the census NAMES the gap instead of hiding it."* The row was authored **specifically to prevent** a gap being hidden, and the generator hid it. `verif/event-surface-census.test.ts` was never fooled, because it reads the VOCAB's bindings rather than the generated table — which is how the two artifacts could disagree for months without either looking wrong alone.
- **THE FIX MAKES THE STEP CHECK INSTEAD OF REWRITE.** Commands may declare `alsoEmitsEvents`; a binding may name any event its command actually commits, and naming anything else **THROWS**. This *keeps* the MarkPwuReady catch — a genuine drift is still not in the declared set — while removing its silence. Verified by running the generator against the vocab **before** the declaration was added: it refused, naming the row. The regenerated table now attributes `REQUESTED → EVIDENCE_PENDING` to `AssuranceEvidenceRequired`, which is what the engine emits.
  - The registry entry gained `alsoEmitsEvents` too, because a runtime table saying a command emits one event while it emits two is the same false declaration one layer over.
  - The test now checks EVERY row against the declared set (plus a control proving the membership test can say no, and that the primary event is still bound somewhere). **Mutation-verified:** deleting the declaration from the generated registry reddens both.
- **Merge target:** Repository — landed. **Status:** CLOSED. Blast radius was contained: `emitsEvent` had exactly one consumer, the unfalsifiable test, so the defect was a false *declaration* rather than a runtime misbehaviour — which is precisely why nothing caught it.

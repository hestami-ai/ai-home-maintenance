# DESIGN — JAN-PFCOV: a coverage floor a strong file cannot satisfy on a weak file's behalf

**Programme:** `JAN-PFCOV` · **Status:** DESIGN · **Opened:** 2026-09-12 ·
**Occasioned by:** the sponsor, on reading `JAN-CSAAEXT` S9's result — *"I do think that we should change to
per-file floor."*

---

## 1. The defect, which is real and is not a threshold breach

JPWB's ratchet is **one global threshold over a merged population**: branches `4103/4683 = 87.61%` against a
floor of 83. It passes. ⛔ **And it passes in a way that cannot distinguish "every file is adequately covered"
from "the average is."**

Measured today, 106 files:

| | |
| --- | --- |
| files below the 83 branch floor **individually** | **24** |
| worst | `rph-projections/src/pwu-behavior.ts` at **60.0%** |
| largest single gap | `rph-application/src/handlers/decomposition.ts` — 75.0%, **45 uncovered branches** |

⭑ **AND S9 DEMONSTRATED THE FAILURE MODE RATHER THAN ARGUING IT.** That increment added 126 branches across five
files. The global number rose 84.92 → 87.61. **Not one of the 24 weak files moved**, and nothing in the gate
said so. A file can be improved to conceal a file that was not.

⚠ **THIS IS THE SAME SHAPE AS THE DEFECT `JAN-CSAAEXT` EXISTED TO FIX**, which is why it is worth taking
seriously rather than treating as tidiness. CSAA's 266 files sat in the denominator and held branch coverage at
91.43% while JPWB's own was 84.92%. Removing them did not change any file's coverage; it changed what the
average was an average OF. ⭑ **An aggregate is a claim about a population, and it is silent about every member.**

---

## 2. The sponsor has decided WHETHER. This design is about HOW — and the obvious route is refuted

**Vitest supports two mechanisms, both confirmed in its shipped source** (`vitest/dist/chunks/coverage.DM_a_rWm.js`):

- **`thresholds.perFile: true`** (`:861`, `:886`) — applies the four thresholds to **every file individually**.
- **Glob-keyed thresholds** (`:816-838`) — `thresholds: { '<glob>': { branches: N } }`, evaluated over the
  **aggregate of matched files**. ⭑ The code's own comment settles a question the docs do not:
  *"Global threshold is for all files, even if they are included by glob patterns"* — so globs are **ADDITIVE**,
  not replacements.

### ⛔ `perFile: true` IS REFUTED BY MEASUREMENT, AND THIS IS THE DESIGN'S CENTRAL FINDING

`perFile` is a BOOLEAN. It changes how the **same four numbers** are applied — there is no second set. So turning
it on means those numbers must hold for every file:

| metric | global floor | files failing if applied per-file | highest uniform per-file floor that passes today |
| --- | --- | --- | --- |
| statements | 95 | **24** | 71.2% |
| branches | 83 | **24** | 60.0% |
| functions | 96.5 | **11** | 50.0% |
| lines | 97 | **24** | 74.6% |

**38 of 106 files fail at least one.** ⛔ So `perFile: true` cannot be enabled at today's numbers, and enabling
it at numbers everything passes would drop the effective floors to **71 / 60 / 50 / 75** — surrendering the
aggregate guarantee to buy the per-file one. ⚠ **That is a trade, not an addition, and it is the opposite of a
ratchet.**

---

## 3. The two routes that survive

### OPTION A — GLOB-KEYED PER-FILE THRESHOLDS IN `vitest.config.ts`

One glob per weak file, pinned at or just below its current value; the global 95/83/96.5/97 stays untouched
because globs are additive.

- ⭑ Native to the gate. No new artifact class, no new reader, failures arrive in the same place as today's.
- ⚠ **A glob matching several files is an AGGREGATE over them** (`:826-831`), so only a glob naming ONE file is
  genuinely per-file. That means ~24-38 single-file entries.
- ⛔ **And it is hand-maintained config** — the defect this repository has recorded most often. Every improved
  file leaves a stale-low pin that nothing reddens, which is the `VERIF_TEST_FLOOR` problem multiplied by 38.

### OPTION B — A JPWB-OWNED RATCHET TEST OVER A COMMITTED PER-FILE BASELINE ⭑ **RECOMMENDED**

A `verif/` test reads `coverage/coverage-summary.json` and a committed per-file baseline, and fails when any file
falls below its recorded figure.

- ⭑ **IT IS THE IDIOM THIS REPOSITORY ALREADY USES FOR EXACTLY THIS.** `slices:ledger:check` and
  `verif/assurance-surface.test.ts` are both committed-baseline ratchets; `scripts/slice-ledger.ts:4-10` records
  why that shape was chosen over a self-rebuilding one.
- ⭑ **The baseline is DERIVED, not authored** — regenerated by its own writer, never hand-edited, so it cannot
  go stale-low by neglect the way 38 config pins would.
- ⭑ **It ratchets**: a file that improves raises its own floor on the next write; a file that regresses reddens
  and names itself.
- ⚠ **It depends on `test:coverage` having run**, so it is a `gate:fast` step AFTER it, not a vitest threshold.
- ⚠ **Rule 2 answered:** the consumer is the gate; what breaks if it is wrong is a file silently regressing
  while the average holds — the exact failure `§1` measures.

---

## 4. What must NOT happen, whichever route is taken

- ⛔ **The global floors do not move.** 95 / 83 / 96.5 / 97, `autoUpdate: false`. This programme ADDS a
  guarantee; it does not rebalance one.
- ⛔ **No per-file floor is set above a file's current value** as part of introducing the mechanism. Introducing
  a ratchet and demanding new work in the same act makes a failure unattributable to either.
- ⛔ **No file is exempted.** An exemption list is a place for a weak file to live permanently, and this
  repository has recorded that shape as `KNOWN`-lists that only ever grow.
- ⚠ **The mechanism must be proven by an observed RED before it is trusted** — a file's figure lowered by hand in
  a disposable copy must fail the check and NAME the file.

---

## 5. Open questions for the sponsor

1. **Option A or B?** Recommended: **B** — derived baseline, ratchets on its own, matches an idiom already in
   the gate twice.
2. **Which metrics get per-file floors?** All four, or branches only? ⚠ Branches is where the spread is (60-100);
   functions has a file at 50% but only 11 offenders. Recommended: **all four**, because a per-file rule that
   covers one metric invites the gap to move to another.
3. **Does this run in `gate:fast` or only in `gate`?** It needs `test:coverage`, which is in `gate:fast` — so it
   can sit immediately after it at no extra cost. Recommended: **`gate:fast`**.
4. ⚠ **Is the ~580 remaining uncovered branches still the priority, or does this displace it?** They interact:
   a per-file ratchet FREEZES the current weakness in place and stops it worsening; it does not reduce it.
   **The two are complementary and neither substitutes for the other.**

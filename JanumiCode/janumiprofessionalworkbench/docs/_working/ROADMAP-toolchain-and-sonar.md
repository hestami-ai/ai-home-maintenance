## 1. The rules this roadmap runs under

Line numbers cite the designs as they are committed with this roadmap: TOOLCUR with the lead's amendment of D-11 step 3 (1,077 lines) and SONARCM with QS3 recorded (981 lines). Paths are relative to `JanumiCode/janumiprofessionalworkbench/` unless they start with a drive letter.

1. **Design → roadmap → build.** The two designs decide behaviour. This roadmap chooses package boundaries, names and order where they leave a choice, and labels each choice it makes. New paths below are where work will go, not files that exist.
2. **One package, then its proof, then the next.** Each package runs on its own branch and worktree and passes `bun run gate:fast` and the extra checks its entry names before its successor starts (`docs/_working/DESIGN-toolchain-currency.md:740`, "own branch and worktree"; `:793`, "Each passes the full gate before the next starts"). A coupling group is a set of tools whose declared ranges make them move together (`:117`, "components that must move together"); a package moves one.
3. **Governed pins move only after a sponsor ruling.** These are the reviewer fingerprint, the decision-model server's identity, the fence digest, the Pi version and a ledger `abolishedBy`, which must name an existing ruling (TOOLCUR D-11 step 4 and I3: `docs/_working/DESIGN-toolchain-currency.md:749-752`, "Governed instruments only after a sponsor ruling"; `:881`, "never re-pinned without a sponsor ruling"). A green gate does not supply that ruling.
4. **Protect the paid runs.** Nothing changes in the main checkout `E:/Projects/hestami-ai` while a paid run is active (`docs/_working/DESIGN-toolchain-currency.md:848`, "Nothing touches the main checkout during a paid run"). The main line is the branch that checkout holds, so a package lands on it only when no paid run is active. Machine software (Node, Edge, Bun) changes only between paid runs, with the sponsor's go-ahead (`:849`). The machine's Node has already moved to 24.22.3 that way (§2), so no package below moves Node, and D-13's rule that "the Node move and T1a's merge into the main line are one step" (`:853`) has nothing left to coordinate.
5. **Branch from the newest main-line tip.** After M0, each package's branch starts from the newest main-line tip, and `bun.lock` is regenerated after merges on that branch (`docs/_working/DESIGN-toolchain-currency.md:845-847`, "a branch from the newest main-line tip"). Ledger entries are named by id; the designs' ledger line numbers are dated (`:868-869`, "names ledger entries by id").
6. **Commits and pushes.** Each commit names its paths explicitly, never `git add -A`, and is made with `git commit -F`. Work branches may be pushed to the public origin after a credential scan; never main, never `--force`. These are the operating rules this work runs under, not new repository policy.
7. **No new register numbers.** Each adoption or decision is filed as a REG-D entry when it lands (`docs/_working/DESIGN-toolchain-currency.md:94`, "assigns no register numbers").
8. **Records are evidence, not a green substitute.** A floor is the oldest version JPWB promises to run on. A baseline is a derived per-file, per-rule count. A re-baseline records a changed measurement. A predicted red is a check's intended failure on a controlled input. A check that could not run is reported as not run, with its reason and residual risk (`docs/_working/DESIGN-toolchain-currency.md:65-66`, "SHALL be reported as not run"; `docs/_working/DESIGN-sonar-configuration-management.md:64-65`, "that may only fall").

**The lead's decision on lint counts that rise (2026-11-13).** A RISE in a Sonar-rule lint count is governed, as SONARCM D-2 says: under the sponsor's QS2 ruling a new finding fails unless it is fixed, recorded as an exception (D-5) or ruled, and that holds for a rise caused by a tool or engine upgrade too. A FALL is ordinary, recorded with the counts before and after. TOOLCUR D-11 step 3's "ordinary re-baseline" covers the other instruments and lint falls only; the lead amends that step of TOOLCUR in the same commit as this roadmap (`docs/_working/DESIGN-toolchain-currency.md:743-748`, "A RISE is not"; `docs/_working/DESIGN-sonar-configuration-management.md:479-481`, "a rise is governed"). A re-baseline under a new engine version is governed too (SONARCM D-4, `docs/_working/DESIGN-sonar-configuration-management.md:534-535`, "a governed act"). Everywhere below, §1's lint rule means this paragraph.

**One text the designs time differently.** TOOLCUR gives the four ES2022 texts to T1c; SONARCM wants the findLast note in `scripts/mutants/run.ts` restated in the same commit as its fix (`docs/_working/DESIGN-toolchain-currency.md:801`, "the 4 restated texts"; `docs/_working/DESIGN-sonar-configuration-management.md:791-794`, "lands in the same commit as the restatement"). **This roadmap's choice:** T1c restates the note's language level; T4 restates its fix wording again in the commit that lands the fix; the S6325 marker in the same comment block follows T4 (X1). Neither package claims a deferred fix has landed.

## 4. Work packages

**How to read an entry.** Every entry's checks include the full §6 gate. "Ordinary re-baselines" means running the relevant writers and recording the counts before and after in the same commit, never hand-editing their output: `bun run gen`, `coverage:floor`, `guards:export`, `slices:ledger` and ledger re-anchoring (TOOLCUR D-11 step 3, `docs/_working/DESIGN-toolchain-currency.md:743-748`, "Ordinary re-baselines in the same commit"). A lint count that falls is ordinary; one that rises, and any re-baseline under a new engine version, are governed (§1's lint rule). An entry that moves no output records that. Every upgrade package starts with D-11 step 1's dry run in scratch: "an integrity-checked copy, no repository change" (`docs/_working/DESIGN-toolchain-currency.md:741`). New script and test names are this roadmap's choices; the designs' ids (D-n, F-n, I-n, J-n, V-n) stay the acceptance source. Each red is a prediction until its package records the red's message and the conditions that stayed green (`docs/_working/DESIGN-toolchain-currency.md:929-930`, "the check asserts its message").

### N0 · Fix what the Node 24.22.3 update broke on the main line

- **Scope.** The machine's Node moved from 24.11.1 to 24.22.3 on 2026-11-13 (§2) before any gate step had run on it. D-11 asks for a dry run in scratch first and for a floor lane (`docs/_working/DESIGN-toolchain-currency.md:741`, "A dry run in scratch"; `:763`, "A floor lane"). The lead then ran every `gate:fast` step to its end on 24.22.3 at the main-line tip `4e05ee0d`, with `TURBO_FORCE=true`, because turbo's cache key does not include the runtime. Two things broke, and both still pass on the official 24.11.1 and 24.15.0 zips:
  1. **The Phase 7 archive.** From Node 24.21.0, `node:sqlite`'s `backup()` refuses `{ rate: -1 }` with a RangeError (`ERR_OUT_OF_RANGE`: the rate must be a positive integer). This is nodejs/node#64893, a fix for a hang at rate 0 (#64892); 26.8.0 has it too, and 22.23.5 does not. `scripts/phase7/run-archive.ts:212` asks for that rate for every archived store. So a paid run on this machine throws at its first archive, after that unit's calls are paid for. That archive also cannot be retried in place: `archiveUnit` first makes the folder and writes `introspect.json`, and it refuses a folder that already exists (`run-archive.ts:1116-1122`). In the gate this turned 6 tests red in `verif/phase7-run-archive.test.ts` and 2 in `verif/phase7-half-b.test.ts`.
  2. **REG-F-501's CONTROL.** Instead of the reset, `apps/rph-demo/src/lib/server/harness-keep-alive-connection.test.ts:135` receives `{ answered: 200, sameConnection: false }`. Node 24.22.1's fix for CVE-2026-105481 (also in 22.23.4 and 26.12.1) makes `http.Agent` check a pooled socket before reusing it, without reading from it. An unread close counts as something waiting, so the agent opens a new connection. The reset REG-F-501 records is narrowed, not gone. A sweep of 153 connections through Playwright's own request API reset 8 of 459 requests on 24.22.3 and 55 of 459 on 24.15.0. With remedy 1's keep-alive figure it reset none of 153 on either Node, one run each. The load was synthetic. So remedy 1 stays, and REG-F-501 stays open.

  Nothing else went red. Steps 1 to 8, `apps/rph-demo`'s check and `gate:tail` (the e2e suite) passed. `coverage:floor:check` failed only because `test:coverage` wrote no summary. Each cause was traced to its Node release through the changelogs, the source at each tag and runs on up to ten official builds, and a second agent re-checked every finding; both are in the lead's scratch record. N0 fixes the two breaks in the main line's own code and upgrades nothing.
- **Depends on.** Nothing: its branch starts from the newest main-line tip. Landing it needs a time when no paid run is active, the sponsor's go-ahead, and a heads-up to the other session through the sponsor, because it edits files that session works in: `scripts/phase7/`, `scripts/mutants/ledger.ts` and the REG-F-501 test. It lands before M0 (§5).
- **Required changes (files, by path).**
  - `scripts/phase7/run-archive.ts`: an exported `ONE_STEP_RATE = 2 ** 31 - 1`, passed at `scripts/phase7/run-archive.ts:212`, so a store is still copied in one step. It is the largest rate `node:sqlite` takes on every Node measured; every Node refuses 2 ** 31 as not an integer. Its docstring is restated, and so is the header's note on the ExperimentalWarning, which Node no longer prints from 24.15.0.
  - `verif/phase7-run-archive.test.ts`: its CONTROL at `verif/phase7-run-archive.test.ts:180` calls `backup()` with `ONE_STEP_RATE`, as `backupStore` does. One new test holds the one-step property itself: a store larger than `node:sqlite`'s default step of 100 pages is copied with no progress call.

  - `scripts/mutants/ledger.ts`: PQ7-M200 is re-anchored on the new line 212 of `scripts/phase7/run-archive.ts`. P6K-M1 and P6K-M11 are re-measured, because the reds they quote change on 24.22.3. ## 6. The gate package: what "done" means per package

**The gate runs in full.** After T0 adds its first step, the sequence is:

```text
bun run toolchain:check
bun run slices:ledger:check
bun run guards:export:check
bun run gen:check
bun run tracker:build
bun run check-types
bun run lint
bun run boundary
bun run build
bun run test
bun run test:coverage
bun run coverage:floor:check
(in apps/rph-demo) bun run check
(at the repository root) bun run gate:tail
```

The chain after the first line is `package.json:27`'s ("bun run slices:ledger:check && bun run guards:export:check"). T0 adds only the first step (`docs/_working/DESIGN-toolchain-currency.md:674`, "`toolchain:check` runs first"). `gate:tail` runs `reviewer:qual:check` and the app's `e2e` (`scripts/gate-tail.ts:25-28`), "BOTH, ALWAYS" (`:5`), and returns the worse exit (`:34-39`, "whatever the ones before it returned"). A targeted test run is not this gate.

**A package's evidence record holds:** the exact base and commit and the paths; for an upgrade, D-11 step 1's dry run, its integrity-checked inputs and its result (`docs/_working/DESIGN-toolchain-currency.md:741`, "an integrity-checked copy, no repository change"); runtime and tool versions; each predicted red, its message and the conditions that stayed green; the final gate result; the extra checks' results; ordinary baselines before and after; any ruling and its register entry; checks not run, with reason and residual risk. This is this roadmap's shape for D-11 step 8, "Records: the matrix, the register entry, and the currency report" (`:770`).

| Extra check | When an entry names it | What its result does and does not prove |
| --- | --- | --- |
| `bun run mutants:changed --run --range=<package base>..HEAD` | Source or config edits that can touch a declared guard. | Without `--run` it only lists the guards over the diff (`scripts/mutants/scope.ts:161`). With it, exit 1 means a guard over the change "SURVIVED its mutant" (`:18`), and exit 2 that the instrument did not run, for example on unstaged changes (`:183`, "INSTRUMENT DID NOT RUN").

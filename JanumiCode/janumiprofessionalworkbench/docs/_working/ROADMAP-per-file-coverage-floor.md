## 0. The three decisions the design left open, taken here

`§5` put four questions. `Q1` is the sponsor's and is answered: **Option B**. The rest are detail the sponsor
has been delegating, so they are decided here with reasons rather than put back:

- **`Q2` — which metrics?** ✅ **All four.** A per-file rule covering one metric invites the gap to move to
  another, and the measurement shows the spread is not confined to branches: functions has a file at 50%.
- **`Q3` — which gate?** ✅ **`gate:fast`, immediately after `test:coverage`.** It needs that step's output and
  nothing else, so it costs one comparison of a JSON file.
- **`Q4` — does this displace the ~580 uncovered branches?** ⛔ **No, and the two must not be confused.** This
  FREEZES the present weakness and stops it worsening. It reduces nothing. Both are owed.

## 1. ⚠ ONE REFINEMENT ON THE DESIGN, STATED RATHER THAN SLIPPED IN

The design and the sponsor both say **floor**, which reads as *"each file must stay above N%"*. ⛔ **The
implementation records UNCOVERED COUNTS, not percentages**, and the difference is worth a paragraph because it
changes what the gate says.

| | percentage floor | uncovered-count ceiling ⭑ chosen |
| --- | --- | --- |
| add covered code | pct rises — passes | uncovered unchanged — passes |
| **add UNCOVERED code** | ⚠ pct may still rise if the file grows — **passes** | uncovered rises — **FAILS** |
| rounding drift 87.61 → 87.60 | ⚠ fails spuriously | unaffected |
| delete code | pct moves either way | uncovered falls; next write tightens it |

⭑ **THE SECOND ROW IS THE WHOLE ARGUMENT.** A percentage floor lets a file add uncovered branches as long as it
adds enough covered ones alongside — the same averaging defect as the global floor, reproduced inside one file.
A count ceiling says the thing actually wanted: **you may not add uncovered code.**

⚠ It is stricter, and that is disclosed: a file gaining one uncovered branch fails even if its percentage
improves. That is the intended behaviour, not a side effect.

## 2. The steps

### S1 · The writer and the derived baseline

**WHAT:** `scripts/coverage-floor.ts --write` reads `coverage/coverage-summary.json` and writes
`verif/coverage/per-file-floor.baseline.json`: per file, the uncovered count for each of the four metrics.
Modelled on `scripts/slice-ledger.ts`, whose header explains why a committed artifact beats a self-rebuilding one.

⛔ **NEVER HAND-EDITED.** It is derived; it is regenerated by its writer in the same commit as the change that
moved it, exactly as `csaa:inventory`'s baseline was and as `slices:ledger` is.

**CONSUMER (Rule 2):** the S2 check. What breaks if it is wrong: a file regresses and the gate says nothing.

---

### S2 · The check, with TWO limbs

`scripts/coverage-floor.ts --check`, and a `verif/` test that drives it.

1. ⛔ **RATCHET:** no file's uncovered count may EXCEED its baseline, for any of the four metrics. A violation
   NAMES the file, the metric, the baseline and the measured value — never a bare count.
2. ⛔ **POPULATION:** the baseline's file set must equal the measured file set. A file added or removed without
   a regenerated baseline FAILS. ⭑ Without this limb a new file with uncovered code is invisible, which is the
   hole the whole mechanism exists to close — and it is the `slices:ledger:check` shape: *regenerate it in the
   same commit as the change that moved it.*

⚠ **THE TWO LIMBS MUST FAIL SEPARATELY.** A file that regresses trips limb 1 alone; a file added trips limb 2
alone. If one mutation trips both, they are one check wearing two names — that is `REG-F-099`'s recorded shape
and it is checked in S4.

---

### S3 · Wire it into `gate:fast`

**PRE:** S1, S2 green. **WHAT:** `coverage:floor:check` joins `gate:fast` directly after `test:coverage`.
`gate:fast` goes 11 → 12 steps.

⚠ **AND `verif/assurance-surface.test.ts`'s `gate:fast` composition pin MUST BE UPDATED IN THE SAME COMMIT** —
it asserts the full ordered step list and will redden. ⭑ That is the pin working: it was written in
`JAN-CSAAEXT` S4 precisely so a step cannot appear or vanish unnoticed. Its floor of 7 root commands rises to 8.

---

### S4 · Prove it, with observed reds

⛔ **No step here is done on green evidence.** On a **disposable copy**, each observed and quoted:

| mutation | must redden | must stay green |
| --- | --- | --- |
| lower one file's baseline uncovered count by 1 | limb 1, naming that file and metric | limb 2 |
| delete a file's baseline entry | limb 2, naming the file | limb 1 |
| add a source file with an uncovered branch | limb 2 | limb 1 |
| blind the reader (point it at a missing summary) | ⚠ must FAIL LOUDLY, never pass as "nothing to check" | — |

⭑ The last row is the one that matters most: a checker that treats an absent input as success is the
control-that-cannot-fail this repository keeps recording.

**Then:** ledger entries for both limbs, each naming its `expectRed` victim. ⚠ `bun run mutants` needs a STAGED
tree.

---

### S5 · Land the baseline as it is

⛔ **The baseline is written from TODAY'S measurement, unchanged.** No file's number is tightened as part of
introducing the mechanism — introducing a ratchet and demanding new work in one act makes a failure attributable
to neither. The 24 files below 83% branches are recorded where they are, and frozen there.

⛔ **No exemption list.** An exemption is where a weak file lives permanently.

---

## 3. What this does NOT do

- ⛔ **It does not move the global floors.** 95 / 83 / 96.5 / 97, `autoUpdate: false`, untouched. This ADDS a
  guarantee.
- ⛔ **It does not reduce the ~580 uncovered branches.** It stops them growing. `REG-F-390`'s residual stands.
- ⚠ **It cannot see a branch that is covered by a test asserting nothing.** Coverage counts execution; only a
  mutant proves discrimination. Stated because a per-file coverage ratchet reads as a stronger guarantee than it
  is.

## 1. Two corrections to the design, from the mechanics pass

⛔ **DESIGN §6 ITEM 4 IS MIS-SHAPED, AND THE SHAPE MATTERS FOR WHAT GETS RATIFIED.** It asks *"whether workspace
content is PER-8 participating material."* **PER-8 classifies per OBJECT by a PAST-TENSE ACT**, not per content
kind. So the ratifiable question is not *"are workspace files participating material"* but *"which object, having
done what, carries this content."* Reshaped in §10.

⛔ **`Workspace.purge` CANNOT MIRROR `ArtifactStore.purge` EXACTLY, AND I ASSERTED IT COULD.** The store's
purgeability class **is part of the storage key** —
`` `${input.tenantPrefix}/${input.purgeability}/${contentHash.slice(7)}` `` — which is how one flat key space
keeps retention legible. **A workspace is path-named, not content-addressed, so it cannot carry the class in its
address.** The mirror is therefore partial by construction: same `purge(address) → PurgeOutcome` signature, same
tombstone rule, and a *declared* rather than *addressed* purgeability. That difference is designed in §3, not
assumed away.

⭑ What DOES carry over verbatim, and must: `purge` takes one argument and no actor, clock or reason
(`ports/artifact-store.ts:107`); the semantics are **"Remove the BYTES and keep the ENTRY"**, because
*"an `ARTIFACT` record referencing a purged key must stay EXPLICABLE"*; and `Purgeability` has exactly two
members and is **"DELIBERATELY NOT A RETENTION CLASS"** (`REG-Q-056` is OPEN). ⛔ **Do not coin a third member
and do not add a retention class here.**

**OBSERVED REDS, in order.** (1) un-skipping the pinned unit test: `1 failed | 25 passed`, the

⭐ **THE CONTAINMENT DEFECT IS CLOSED AT THE SIGNATURE, NOT AT THE CALL SITE.** `OpenProducerSession` now takes a
`ProducerSessionContext` carrying the Undertaking's sandbox, and `producerWorkingDirectory` is the ONLY thing
that may answer where a producer runs. **It has no fallback arm, and that absence is the guarantee** — every
refusal has an obvious "reasonable" repair (use the server's directory) and that repair IS the defect. Both

⭐ **THE ROOT IS DERIVED FROM `JPWB_DEMO_DB` RATHER THAN FROM A SECOND ENV KEY, AND THE REASON IS AN ORPHAN THE
REPOSITORY HAS ALREADY MEASURED.** The roadmap said "one durable root from one env key"; taking that to mean a
NEW key would let an operator configure a durable record plane whose deliverable evaporates at restart — exactly
the inverse orphan `ArtifactStore.durability` exists to prevent (*"a permanent record names a `storageKey`
whose store answer, after one restart, is byte-indistinguishable from a key that was never stored"*).
`getArtifactStore()` already derives the content plane from the record plane's key; the workspace root derives
the same way (`${DB_PATH}.workspaces/<undertakingId>`). One key configures all three planes or none.

⭐ **`R8` IS CARRIED BY THREE DECLARATIONS, NOT ONE, AND TWO OF THEM ARE INVISIBLE TO BEHAVIOUR.**
`ownerKind: 'UNDERTAKING'` and `purgeability: 'RETAINED_BY_PARTICIPATION'` change nothing a read can see — files
are written, files are read — so each needed an assertion of its own. ⚠ **`P2-k` SURVIVED THE FIRST RUN**: the
purgeability declaration was untested, and the only thing that exposed it was asking the workspace to DESTROY
the product and requiring it to refuse. That is the instrument doing its job, recorded rather than quietly
fixed.

⚠ **THE FILESYSTEM ADAPTER NEEDED A TOMBSTONE RECORD, WHICH THE IN-MEMORY DEFAULT GETS FOR FREE.** `purge`
promises *"Remove the BYTES and keep the ENTRY"*, and a path on a filesystem has only two states — present or
absent — so neither truncating (which reads as an EMPTY FILE, a different fact) nor unlinking can carry "purged
on schedule" as distinct from "never written" and from "lost". The entry therefore lives in a record beside the
files, and that record is a RESERVED path: a step that could write it could rewrite the retention history of
everything else in the workspace. ⭑ Its refusal is DISTINCT from the containment refusal, because a caller
naming the record has not tried to escape and telling it that it did would be false.

**PROOF — EVERY LIMB BY AN OBSERVED RED, 16 declared mutants, `bun run mutants P2-` → 17 of 17 KILLED (the

### ⭐⭐ `W2` — WHY THE BOUND IS STRUCTURAL AND NOT A MEMBERSHIP TEST, WHICH IS THE PART THAT NEEDED DECIDING

Three options were open, and **(a) had to be ruled out before (b) could be taken**.

**(a) VALIDATE THE NAME AGAINST THE HOST'S ACTUAL MINTED SET — NOT AVAILABLE, and the reason is a ruling this
repository already made.** The minted set is SESSION-SCOPED and known only to the adapter that opened the
session (`AdapterToolObservation.mintedToolNames`); the kernel is host-agnostic and cannot reach into an app
adapter. Minting the set into the wire vocabulary instead is refused by `backing-tool.ts`'s own recorded
position — *"of the 100 closed enums in the ratified contracts NOT ONE names a tool, agent, provider, CLI or
vendor, and `PER-2` would make a deployment fact permanent."* And carrying the set **in the payload beside the
name** re-creates the defect exactly: the caller would declare both halves and the check would be
self-consistency again, which is `W1`'s shape.

**(b) BOUND THE SHAPE — TAKEN.** `RecordPlaneNameSchema`: at most 64 characters, and `^[A-Za-z][A-Za-z0-9_.-]*$`.
⛔ The character class is chosen for what it EXCLUDES: no backslash, slash or colon (no path), no `=` (no
`KEY=value`), no space, no control character (no NUL). ⚠ **AND IT IS SAID TO BE WEAKER THAN (a):** it does not
establish that the name was minted, that the tool exists, or that the host and not the model chose it. Only
that the value has the SHAPE of a name — which is a property of the VALUE rather than of a caller's honesty.

⭐ **AND IT LIVES IN THE CONTRACT RATHER THAN IN THE HANDLER, WHICH IS WHAT MAKES IT A BOUNDARY AT ALL.** A
handler check governs ONE write path — the command payload. A bound on the schema governs three:
`validateAgainst(spec.payload, …)` in `command-bus.ts`, the materialized object state in `kit.ts`, and the
ratified event payload beside it. `B8`'s verdict in this same programme was that *a convention with zero
production call sites is not a control*; enforcing at the producer and calling it enforced at the boundary is
that error one layer up, and the review named it as such.

**MECHANISM.** The vocabulary gained a `bound` attribute; `gen-objects.ts` gained a small closed table of named
bounds and **THROWS on one it does not know** (the posture `gen-messages.ts` already takes for an unresolvable

fields declare one. No generated artifact was hand-edited: vocab → `bun run gen` → wiring, and `gen:check` is

### ⛔⛔ `B-1` — THE ONE BREACH THAT IS A DEFECT UNDER THE RULINGS TOO

**§22.1 IS VERBATIM: *"Revoked bindings cannot be used for new attempts."* IT WAS ENFORCED ON ONE ARROW AND

binding held. And every reader in the Phase 3 path took a capability **LIST** and never a **STATUS**: `grantsFor`,

revocation, a revoked binding **minted the full tool surface**, and the repair loop happily took another try.

⚠ **WHY NO ARROW CAUGHT IT, WHICH IS THE PART WORTH KEEPING.** `RPH-EXE-003` really does carry this rule — for
START and RESUME, where `bindingAuthorityVerdict` sits. `JAN-EXECLOOP`'s loop takes SEVERAL TRIES against ONE
already-started step and **dispatches no command between them**, and Phase 3 mints a tool surface at session
open, through no arrow at all. A per-arrow enforcement is complete only while every attempt crosses an arrow.

**FIXED AT TWO SITES, BOTH THROUGH THE KERNEL'S OWN `canReuseBindingForNewAttempt`** rather than a second
spelling of `status !== 'REVOKED'`:

| site | behaviour |
| --- | --- |
| `stepCapabilityRefusal` | FIRST limb, before any capability is examined — so the message names the REVOCATION and not a capability that is in fact granted |
| `mintExecutionTools` | returns an EMPTY surface, so a revoked binding gives a model no hands at all |

⛔ **AND THE ORDER INSIDE `mintExecutionTools` IS ASSERTED:** the whole-catalog NAME BOUND runs FIRST, because it
is a property of the HOST rather than of one grant — returning early would leave an unholdable name dormant for
every revoked binding, which is `P3-d`'s dormancy defect reached by a new road. ⭑ `canReuseBindingForNewAttempt`
consequently LOST its dead-kernel census row, which is that gate's *"good failure"*, and `RPH-EXE-003`'s row was

⚠ **THE RESIDUAL, STATED:** the surface is minted ONCE per held session while the status is re-read every try, so

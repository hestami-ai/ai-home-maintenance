# ROADMAP — `JAN-CRITREAD` L3: building §32's `recordCriterionResult`

**Design:** `DESIGN-the-command-nobody-built.md` · **Date:** 2026-09-20
**Rules:** `RPH-CON-005`, `RPH-ASR-005` · **Findings:** `REG-F-420`, `REG-F-421`, `REG-F-422`

⭑ **Exit:** `recordCriterionResult` is dispatchable, emits the **ratified** `AssuranceCriterionEvaluated`,
refuses a `criterionId` the governing policy does not declare, and commits no state delta. The floor records its
computed criteria through it.

⛔ **THIS ROADMAP DOES NOT UNBLOCK `CR-02`, AND MUST NOT BE READ AS DOING SO.** The gate reads
`validatorResult.claimResults`; dispatching N commands does not change `claimResults: []`. Changing the gate's
subject and wiring the four exposed producers is a **separate** increment (DESIGN §6). Fusing them is what made
the fourth design call false.

## 0. ⛔ The sequencing constraint is not negotiable, and it is measured

`verif/command-dispatch-census.test.ts:93-109` refuses any `COMMANDS` key that no test drives, and its
`UNDRIVEN` allowance is **empty by design**. "Driven" means the PascalCase name appears as a **quoted string
literal in non-comment text of a `*.test.ts`** under `packages/*/src` or `apps/*/src` — ⚠ a production
dispatcher moves this census **not at all**.

`ROADMAP-assessment-lifecycle-restoration.md:193` states the rule this produces:

> *"Events may be declared ahead of emitters; **commands may not**."*

⭐ **SO `CB-02` IS ONE COMMIT AND CANNOT BE SPLIT:** the vocabulary entry, the regenerated contracts, the
handler and its driving test land together or the gate fails.

⚠ **AND `messages.ts` IS GENERATED** — source `vocab/m3-commands-events.json`, regenerated by
`bun run gen:messages`, verified by `gen:check` at **step 3 of 13** in `gate:fast`. Every hand edit to it fails
the gate. Nothing below edits it.

### `CB-01` — ⛔ the payload decision, which ships NO code

The event payload for `AssuranceCriterionEvaluated` has **no §21 contract**; it is the `Source TBD` class. The
§20.1 leaf (`criterionId, result, rationale, evidenceIds` — all required) is its basis, and two of those four
fields the floor cannot honestly fill (DESIGN §5).

**The decision this increment owes, stated so it is decided rather than defaulted:**

| field | the question |
|---|---|
| `rationale` | ⛔ the floor populates it **only on failure** (`validators.ts:322`). Derive a true one from the deciding fact at `floor.ts:182-241`, or relax it? ⚠ Reusing `floor-policies.ts`'s per-criterion rationale is **forbidden** — that is the policy's reason for HAVING the criterion, not the assessment's reason for its OUTCOME. |
| `evidenceIds` | ⛔ absent from `FloorCriterion` entirely. `[]` is *true* for a deterministic structural floor — and indistinguishable downstream from "not asked", which is `REG-D-059`'s manufacture-from-silence shape. |

**Predicted reds:** none — no code. ⭑ The increment is a **written decision with its reasoning**, and `CB-02`
may not start until it exists. This is the increment most likely to be skipped, which is why it is first.

### `CB-02` — the command, the event, the handler and its driving test, in ONE commit

⭐ **MODELED ON `submitEvidenceForAssessment`, NOT `recordAssuranceObservation`** (DESIGN §3). Target
`ASSURANCE_ASSESSMENT`; commit **no state delta** beyond the envelope bump; the fact lives on the event.

⛔ **THE EVENT NAME IS RATIFIED AND MUST NOT BE MINTED.** `AssuranceCriterionEvaluated`, §31 catalog `:1774`,
inside the fence `text id="yl7ymv"`, bound to this command by the §26.5 note at `:1813-1816`. ⚠ A derived name
(`CriterionResultRecorded`) was the mistake this design caught in itself — see `REG-F-422`.

**Guards, in order, each with its own red:**
1. the assessment exists and revision matches (`loadOrReject`)
2. the assessment is `ASSESSING` — criterion results are produced during assessment, not before
3. ⭑ the `criterionId` is one **the governing policy declares** — fail closed, exactly as
   `submitEvidenceForAssessment` validates `satisfiesRequirementId` against declared `requiredEvidence`
   (`assurance.ts:1526-1534`)
4. the `result` is a ratified `CriterionResultOutcome`

**Predicted reds:**

| Mutant | Must redden |
|---|---|
| delete the declared-criterion guard (3) | a result recorded against a criterion the policy never declared is accepted |
| widen the state window to `submitEvidenceForAssessment`'s `['EVIDENCE_PENDING','READY','ASSESSING']` | the window test — a criterion result before assessment began is a judgement nobody made |
| emit a minted event name instead of the ratified one | ⭐ the §31 fidelity check — and if no such check exists, **this increment owes one**, because nothing else would catch it |
| mutate the assessment snapshot | the no-state-delta test, `submitEvidenceForAssessment`'s own invariant one axis over |
| **CONTROL** | a well-formed result against a declared criterion on an `ASSESSING` assessment is ACCEPTED and appends exactly one event |

⚠ **THE THIRD MUTANT IS THE ONE TO CHECK FIRST.** If no gate compares declared event names against §31, then
the ratified-vocabulary fidelity this increment depends on is unguarded — which is itself a finding.

### `CB-03` — the floor records its criteria through it

`record-assurance.ts` already computes every criterion (`a.criteria`) and drops them at the boundary
(`:174-183`). It dispatches one `recordCriterionResult` per criterion before `CompleteAssuranceAssessment`.

⛔ **`recordAssuranceRecordingPlan` THROWS on any refusal** (`:122`), so one refused criterion takes down the
whole floor recording. The guard at `CB-02`(3) must therefore be satisfiable by every criterion the floor
computes — ⭑ which is exactly what `CB-01`'s decision determines, and why it comes first.

**Predicted reds:**

| Mutant | Must redden |
|---|---|
| drop the per-criterion dispatch | the accumulation test — the assessment's event log carries no criterion results |
| map `outcome` → `result` without the rename | the vocabulary test — `FloorCriterion.outcome` and §20.1's `result` are the same enum under two names |
| synthesize a rationale from `floor-policies.ts` | ⛔ the conflation test (DESIGN §5) — the policy's reason for having a criterion is not the assessment's reason for its outcome |
| **CONTROL** | `record-assurance.test.ts` stays green — all 4 tests, including *"a fully-satisfied floor records one SATISFIED assessment per policy"* |
